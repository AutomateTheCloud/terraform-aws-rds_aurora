# Terraform module for Amazon Aurora clusters

Creates an Amazon Aurora PostgreSQL or Aurora MySQL cluster, its DB instances, and a security group that controls who can connect. Optional settings cover backups and maintenance windows, exported logs, Enhanced Monitoring, Performance Insights, IAM database authentication, Aurora Auto Scaling of readers, restoring from a snapshot, and joining an Aurora global database.

The defaults are the settings most production databases should have. A cluster created with only the required inputs is encrypted, keeps its master password in AWS Secrets Manager instead of in Terraform state, cannot be reached over the network until you allow a source, has no public address, refuses to be deleted, and takes a final snapshot when it is.

## What it configures

| Setting | Default | Input |
|---|---|---|
| Encryption at rest | Always on, with the AWS managed key `aws/rds` | `kms_key_id` |
| Master password | Generated by RDS and kept in Secrets Manager | `master_password` |
| Network access | None: no client can connect | `security_group_ingress` |
| Outbound connections | None | `security_group_egress` |
| Public IP addresses | None | `instances.publicly_accessible` |
| Deletion protection | On | `deletion_protection` |
| Final snapshot on delete | Taken and kept | `skip_final_snapshot` |
| Instances | One writer, no standby | `instances.count` |
| Automated backups | Kept for 7 days | `backup` |
| Minor version upgrades | Applied by AWS in the maintenance window | `maintenance` |
| Exported logs | None | `cloudwatch_logs` |
| Enhanced Monitoring, Performance Insights | Off | `instances` |
| IAM database authentication | Off | `iam_database_authentication_enabled` |
| Auto Scaling of readers | Off | `autoscaling` |

## Usage

```hcl
module "orders_db" {
  source  = "AutomateTheCloud/rds_aurora/aws"
  version = "~> 1.0"

  details = {
    scope       = "Automate the Cloud"
    purpose     = "Orders Database"
    environment = "Production"
  }

  name                 = "orders"
  engine               = "aurora-postgresql"
  vpc_id               = "vpc-0123456789abcdef0"
  db_subnet_group_name = "private"

  instances = {
    instance_class = "db.r6g.large"
    count          = 2
  }

  security_group_ingress = {
    app = { security_group_id = "sg-0123456789abcdef0", description = "Application servers" }
  }
}
```

`details`, `name`, `engine`, `vpc_id`, `db_subnet_group_name` and `instances.instance_class` are the only required inputs. `details` sets the `Scope`, `Purpose` and `Environment` tags on every resource.

Applications connect to `module.orders_db.metadata.rds_cluster.endpoint` for reads and writes, or `reader_endpoint` for reads only, on `metadata.rds_cluster.port`. The master password is in the Secrets Manager secret whose ARN is `module.orders_db.metadata.rds_cluster.master_user_secret[0].secret_arn`.

The module uses your default `aws` provider and creates everything in that provider's Region. To create the cluster somewhere else without configuring another provider, set `region`:

```hcl
module "orders_db_us_west_2" {
  source  = "AutomateTheCloud/rds_aurora/aws"
  version = "~> 1.0"

  region               = "us-west-2"
  details              = { scope = "Automate the Cloud", purpose = "Orders Database", environment = "Production" }
  name                 = "orders"
  engine               = "aurora-postgresql"
  vpc_id               = "vpc-0abcdef0123456789"
  db_subnet_group_name = "private"
  instances            = { instance_class = "db.r6g.large" }
}
```

The VPC, the DB subnet group and any KMS key must be in that Region too. The Enhanced Monitoring role is an IAM role, which is global; its name says which cluster and Region it is for.

To use a provider configured for another account, pass it explicitly with `providers = { aws = aws.other_account }`.

## The `details` input

Most modules ask only for what the resource itself needs. This one also requires `details`: three names that say what the cluster belongs to, what it is for, and which environment it is in. Every Automate the Cloud module takes the same input, and requiring it is deliberate.

```hcl
details = {
  scope       = "Automate the Cloud" # what it belongs to: an organization, team or project
  purpose     = "Orders Database"    # what it is for
  environment = "Production"         # which environment
}
```

**Every resource can be traced.** The three names become the `Scope`, `Purpose` and `Environment` tags on every resource the module creates. Months later, anyone looking at a cluster in the AWS console, or at a line on the bill, can see who it belongs to and why it exists. With cost allocation tags turned on in AWS Billing, the same tags split your bill by project and environment. Because the input is required and checked, no resource can be created without them.

**One definition for a whole stack.** Write `details` once and pass the same value to every module, so the database, its network, its encryption key and everything else are tagged alike. Tags you want everywhere, such as a cost center or the Terraform workspace, go in `additional_tags`:

```hcl
locals {
  details = {
    scope           = "Automate the Cloud"
    purpose         = "Orders Database"
    environment     = "Production"
    additional_tags = { CostCenter = "1234", IaC = "true" }
  }
}

module "orders_db" {
  source  = "AutomateTheCloud/rds_aurora/aws"
  version = "~> 1.0"

  details              = local.details
  name                 = "orders"
  engine               = "aurora-postgresql"
  vpc_id               = "vpc-0123456789abcdef0"
  db_subnet_group_name = "private"
  instances            = { instance_class = "db.r6g.large" }
}
```

**Consistent names.** The module turns each name into two short forms other resources can be named with: `abbr`, lowercase with words joined by underscores (`Orders Database` becomes `orders_database`), and `machine`, lowercase letters and numbers only (`ordersdatabase`), for resources that allow no underscores. It also works out a short form of the Region, such as `use1` for `us-east-1`. Every module derives these the same way, so names stay consistent across a stack. To choose your own short forms, set `scope_abbr`, `purpose_abbr` or `environment_abbr`, for example `environment_abbr = "prd"`.

**One output to reach everything.** All of it comes back in the `metadata` output, along with everything the module created, so a configuration needs only one reference: `module.orders_db.metadata.rds_cluster.endpoint` for the address applications connect to, or `module.orders_db.metadata.aws.region.abbr` for the Region's short form.

## Things to know

### Deleting a cluster

Deletion protection is on by default, so RDS refuses to delete the cluster, which holds the data. To delete the cluster, first set `deletion_protection = false` and apply, then destroy.

Deletion protection covers the cluster, not its instances. If you run `terraform destroy`, or apply a change that replaces the cluster, while it is on, Terraform deletes every instance first, which took about 10 minutes in testing, and only then fails on the cluster. The data is safe, but nothing can connect to it until you apply again, which creates the instances again. Read the plan: a line saying the cluster `must be replaced` or `will be destroyed` means this.

Deleting the cluster first takes a final snapshot named `<name>-final-<8 hex digits>`, unless `skip_final_snapshot` is `true`. The final snapshot, and any manual snapshot, is kept and billed until you delete it. To start a new cluster from a final snapshot, pass its name in `snapshot_identifier`.

### Settings that replace the cluster

Changing `name`, `engine`, `db_subnet_group_name` or `kms_key_id`, including setting a key later, replaces the cluster: Terraform deletes it and creates an empty one. Deletion protection stops the cluster from being deleted, though not its instances (see above). Choose these before you store data.

Some settings are used only when the cluster is created, and changing them later does nothing: `database_name`, `master_username`, `snapshot_identifier` and `global_cluster`. Create databases and users with SQL after that.

Most other settings change in place. RDS holds some changes, such as a new instance class, until the next maintenance window unless `maintenance.apply_immediately` is `true`. Until RDS makes such a change, every plan shows it again; applying that plan again changes nothing. Some changes restart the instances.

### The master password

By default RDS generates the master password and keeps it in a Secrets Manager secret that RDS manages, so it never appears in Terraform state or plans. Read it with `aws secretsmanager get-secret-value --secret-id <secret ARN>`, or let applications read it with an IAM policy that allows `secretsmanager:GetSecretValue` on that secret (and `kms:Decrypt` on `master_user_secret_kms_key_id`, if you set one). RDS rotates it every 7 days by default; applications should read the secret when they connect instead of keeping a copy. Secrets Manager bills for each secret.

If the password must come from somewhere else, pass it in `master_password`. Terraform then stores it in plain text in its state, so protect the state. Switching between the two updates the cluster in place, and the first plan afterwards shows only `metadata` changing; applying that plan changes no resources.

The secret's KMS key, `master_user_secret_kms_key_id`, is fixed when RDS creates the secret: AWS refuses to change it. When you stop using `master_password`, RDS creates a new secret encrypted with the AWS managed key `aws/secretsmanager`, even when `master_user_secret_kms_key_id` is set, because the AWS provider does not send the key again. `metadata.rds_cluster.master_user_secret[0].kms_key_id` shows the key in use.

For applications, IAM database authentication (`iam_database_authentication_enabled`) avoids passwords altogether: each connection uses a short-lived token signed with the application's IAM credentials. It still needs a database user set up for it with SQL.

### Network access

The module's security group allows the database port, over TCP, from the sources in `security_group_ingress`, and nothing else. It has no outbound rules: a database answers its clients without them. Add `security_group_egress` only for features that make the database connect out, such as loading data from Amazon S3 or invoking AWS Lambda functions; those also need an IAM role associated with the cluster (`aws_rds_cluster_role_association`, outside this module) and a route to the service, such as a VPC endpoint.

To let another resource in, use its security group as the source, so the rule follows the resource as its addresses change. Use the module's group, `metadata.security_group.id`, as the destination in that resource's own outbound rules.

Use private subnets for `db_subnet_group_name`. `instances.publicly_accessible` gives the instances public addresses, which, in subnets with a route to an internet gateway, lets anyone on the internet whom `security_group_ingress` allows reach the database. Prefer a private connection, such as a VPN or AWS Systems Manager port forwarding through an instance in the VPC.

### Instances and failover

One instance is created as the writer, whichever RDS creates first, and the others as readers in the Availability Zones RDS chooses. If the writer fails, RDS promotes a reader, preferring the lowest promotion tier; the module gives `<name>-1` tier 0, `<name>-2` tier 1, and so on. With one instance there is no reader to promote, and [AWS documents](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Concepts.AuroraHighAvailability.html) that recovery takes longer. After a failover, `metadata.rds_cluster_instance[*].writer` shows which instance is the writer.

Not every instance class is available for every engine version, Region and Availability Zone, and Performance Insights does not work with every class. Check before you choose: `aws rds describe-orderable-db-instance-options --engine aurora-postgresql --engine-version 17.9 --db-instance-class db.t3.medium`.

### Engine versions

Without `engine_version`, AWS uses the engine's current default version, and the cluster keeps it until it is upgraded. Raising `engine_version` upgrades the cluster and its instances in place; a new major version also needs `maintenance.allow_major_version_upgrade` and, often, parameter groups of the new family. The instances finish upgrading after Terraform has saved the cluster, so the first plan afterwards shows only `metadata` changing; applying that plan changes no resources and saves the new versions.

With `maintenance.auto_minor_version_upgrade` on, the default, AWS can apply new minor versions in the maintenance window on its own. Terraform then reads the newer version and does not try to change it back, even though `engine_version` still names the older one; `metadata.rds_cluster.engine_version_actual` shows the version the cluster runs.

### Auto Scaling

`autoscaling` lets Aurora Auto Scaling add readers when the readers are busy and remove them when they are not, between `min_capacity` and `max_capacity`. It counts every reader, including the ones in `instances.count`. The readers it adds are named `application-autoscaling-<id>`. Terraform does not manage them, and removing `autoscaling` does not delete them. While any exist, `terraform destroy` deletes the module's own instances, which leaves an added reader as the cluster's only instance, and then fails on the cluster with `InvalidDBClusterStateFault`. Before destroying, set `autoscaling = null` and apply, so no new readers are added, delete the added readers with `aws rds delete-db-instance --db-instance-identifier application-autoscaling-<id>` or in the RDS console, and then destroy.

### Logs

`cloudwatch_logs.exports` sends database logs to CloudWatch Logs. The module creates each log group, `/aws/rds/cluster/<name>/<type>`, before the cluster, so its retention applies from the start; RDS would otherwise create it with no expiry. The `audit` (MySQL), `general` and `slowquery` logs, and PostgreSQL logging of statements, are written only when turned on in the cluster's parameter group, as the [complete example](https://github.com/AutomateTheCloud/terraform-aws-rds_aurora/tree/main/examples/complete) does with `log_min_duration_statement`. Enhanced Monitoring, when on, writes to the `RDSOSMetrics` log group, which RDS creates and the module does not manage.

### Global databases

`global_cluster` makes the cluster a member of an Aurora global database that you create separately, for example with `aws_rds_global_cluster`. Create the primary first, with `global_cluster = { identifier = "..." }`, then each secondary in its own Region with `secondary = true` and a KMS key from that Region. Global databases do not take the burstable `db.t` classes: `describe-orderable-db-instance-options` shows `SupportsGlobalDatabases` for each class, `true` for memory-optimized classes such as `db.r6g.large`. Switching over or failing over between Regions is done outside Terraform.


Default: `null`

#### <a name="input_iam_database_authentication_enabled"></a> [iam_database_authentication_enabled](#input_iam_database_authentication_enabled)

Description: Let database users sign in with AWS Identity and Access Management (IAM) credentials instead of a password. Each database user must still be granted the `rds_iam` role (PostgreSQL) or created with the `AWSAuthenticationPlugin` (MySQL), and the IAM principal needs `rds-db:connect`. Defaults to `false`.

Type: `bool`

Default: `false`

#### <a name="input_kms_key_id"></a> [kms_key_id](#input_kms_key_id)

Description: ARN of the AWS Key Management Service (KMS) key that encrypts the cluster's storage, its snapshots and Performance Insights data. The cluster is always encrypted; without a key, RDS uses the AWS managed key `aws/rds`.

Changing the key, including setting one later, replaces the cluster and deletes its data, because RDS cannot change the key of an existing cluster. With `deletion_protection` on, RDS refuses to delete the cluster, but only after Terraform has deleted its instances.

Type: `string`

Default: `null`

#### <a name="input_maintenance"></a> [maintenance](#input_maintenance)

Description: When and how AWS changes the cluster.

- `window` - (Optional) The weekly time range, in UTC, for maintenance and for changes that are not applied immediately, such as `sun:05:00-sun:06:00`. At least 30 minutes. Without it, AWS picks one.
- `apply_immediately` - (Optional) Apply changes to the cluster and instances at once instead of in the next maintenance window. Some changes restart the instances. Defaults to `false`.
- `auto_minor_version_upgrade` - (Optional) Let AWS upgrade the instances to new minor versions in the maintenance window. Defaults to `true`.
- `allow_major_version_upgrade` - (Optional) Allow a change of `engine_version` to a new major version. Defaults to `false`.

Type:

```hcl
object({
    window                      = optional(string)
    apply_immediately           = optional(bool, false)
    auto_minor_version_upgrade  = optional(bool, true)
    allow_major_version_upgrade = optional(bool, false)
  })
```

Default: `{}`

#### <a name="input_master_password"></a> [master_password](#input_master_password)

Description: The master user's password. Without it, the default, RDS generates the password and keeps it in AWS Secrets Manager, where it can be rotated, and it is never stored in Terraform state; `metadata.rds_cluster.master_user_secret` gives the secret's ARN.

A password given here is stored in Terraform state in plain text. Use it only when the password must come from somewhere else. Printable ASCII characters without `/`, `"`, `@` or spaces: 8 to 99 for Aurora PostgreSQL, 8 to 41 for Aurora MySQL. Changing it, or setting or removing it later, updates the cluster in place.

Type: `string`

Default: `null`

#### <a name="input_master_user_secret_kms_key_id"></a> [master_user_secret_kms_key_id](#input_master_user_secret_kms_key_id)

Description: ARN of a KMS key to encrypt the Secrets Manager secret that holds the master password. Without it, Secrets Manager uses the AWS managed key `aws/secretsmanager`. Not used with `master_password`.

Set it when the secret is created: AWS refuses to change the key of an existing secret. A secret created later, when you stop using `master_password`, is encrypted with `aws/secretsmanager` even when this is set.

Type: `string`

Default: `null`

#### <a name="input_master_username"></a> [master_username](#input_master_username)

Description: The master user's name. Defaults to `postgres` for Aurora PostgreSQL and `admin` for Aurora MySQL. Letters, digits and underscores, starting with a letter: up to 32 characters for MySQL, 63 for PostgreSQL. Each engine also refuses some names when the cluster is created: Aurora PostgreSQL refuses `owner`, for example, and both refuse `rdsadmin`.

Used only when the cluster is created: changing it later does nothing. It is not set on a restore from a snapshot or a global database secondary, which keep the source's master user.

Type: `string`

Default: `null`

#### <a name="input_port"></a> [port](#input_port)

Description: The port the database listens on, from `1150` to `65535`. Defaults to `5432` for Aurora PostgreSQL and `3306` for Aurora MySQL. The security group rules in `security_group_ingress` use it.

Type: `number`

Default: `null`

#### <a name="input_region"></a> [region](#input_region)

Description: The AWS Region to create the cluster and everything else in, such as `us-west-2`. Defaults to the Region of the AWS provider passed to the module.

Type: `string`

Default: `null`

#### <a name="input_security_group_egress"></a> [security_group_egress](#input_security_group_egress)

Description: Where the cluster may connect to. The cluster needs no outbound rules to answer clients, so with the default, `{}`, it can open no connections. Add an entry for a feature that makes the database connect out, such as loading data from Amazon S3 (HTTPS, port `443`, to the S3 prefix list) or invoking AWS Lambda functions. The keys are names you choose; they only identify each rule.

Each entry takes:

- `port` - (Required) The TCP port to allow.

and exactly one of:

- `cidr_ipv4` - An IPv4 range, such as `10.0.0.0/16`.
- `cidr_ipv6` - An IPv6 range, such as `2001:db8::/56`.
- `security_group_id` - A security group whose members the cluster may connect to.
- `prefix_list_id` - A managed prefix list, such as the one for S3 in the Region (`data.aws_ec2_managed_prefix_list` with name `com.amazonaws.<region>.s3`).

and optionally:

- `description` - (Optional) What the destination is. Defaults to the key.

Type:

```hcl
map(object({
    port              = number
    cidr_ipv4         = optional(string)
    cidr_ipv6         = optional(string)
    security_group_id = optional(string)
    prefix_list_id    = optional(string)
    description       = optional(string)
  }))
```

Default: `{}`

#### <a name="input_security_group_ids"></a> [security_group_ids](#input_security_group_ids)

Description: IDs of more security groups to attach to the cluster, besides the one the module creates, such as a group shared by every database.

Type: `list(string)`

Default: `[]`

#### <a name="input_security_group_ingress"></a> [security_group_ingress](#input_security_group_ingress)

Description: Who can connect to the database. The module creates a security group for the cluster that allows the database port (`port`) over TCP from each source listed here, and from nothing else. With the default, `{}`, no client can connect. The keys are names you choose; they only identify each rule, so a security group created in the same configuration can be used.

Each source takes exactly one of:

- `cidr_ipv4` - An IPv4 range, such as `10.0.0.0/16`.
- `cidr_ipv6` - An IPv6 range, such as `2001:db8::/56`.
- `security_group_id` - A security group whose members may connect, such as the group of your application servers.
- `prefix_list_id` - A managed prefix list of ranges.

and optionally:

- `description` - (Optional) What the source is. Defaults to the key.

Type:

```hcl
map(object({
    cidr_ipv4         = optional(string)
    cidr_ipv6         = optional(string)
    security_group_id = optional(string)
    prefix_list_id    = optional(string)
    description       = optional(string)
  }))
```

Default: `{}`

#### <a name="input_skip_final_snapshot"></a> [skip_final_snapshot](#input_skip_final_snapshot)

Description: Delete the cluster without taking a final snapshot. Defaults to `false`: deleting the cluster first takes a snapshot named `<name>-final-<8 hex digits>`, which is kept until you delete it.

Type: `bool`

Default: `false`

#### <a name="input_snapshot_identifier"></a> [snapshot_identifier](#input_snapshot_identifier)

Description: The identifier or ARN of a DB cluster snapshot to create the cluster from, such as a final snapshot of an earlier cluster. The engine must match. The master user and databases come from the snapshot, but the password is set as described in `master_password`.

Used only when the cluster is created: changing it later does nothing.

Type: `string`

Default: `null`

#### <a name="input_storage_type"></a> [storage_type](#input_storage_type)

Description: The cluster's storage configuration: `aurora` (Aurora Standard, billed for each I/O request) or `aurora-iopt1` (Aurora I/O-Optimized, no I/O charges and a higher price for storage and instances). Without it, AWS uses Aurora Standard. It can be changed in place, to I/O-Optimized once every 30 days.

Type: `string`

Default: `null`

#### <a name="input_timeouts"></a> [timeouts](#input_timeouts)

Description: How long Terraform waits for the cluster to be created, updated or deleted, such as `120m`. Each defaults to `120m`.

Type:

```hcl
object({
    create = optional(string, "120m")
    update = optional(string, "120m")
    delete = optional(string, "120m")
  })
```

Default: `{}`

### Outputs

The following outputs are exported:

#### <a name="output_metadata"></a> [metadata](#output_metadata)

Description: Everything the module created, in one object, so that other configurations need only one reference:

- `details` - The scope, purpose and environment, each with its `name`, `abbr` (lowercase, words joined by underscores) and `machine` (lowercase letters and numbers only) forms, and the `tags` applied to every resource.
- `aws` - The `account.id`, and the `region` `name`, `abbr` (such as `use1` for `us-east-1`) and `description`.
- `rds_cluster` - The cluster's `id`, `arn`, `endpoint` (the writer), `reader_endpoint` (the readers, or the writer when there are none), `port`, `engine`, `engine_version_actual`, `master_username`, `master_user_secret` (a list with the Secrets Manager secret's `secret_arn`, when RDS keeps the password), `cluster_resource_id` (for IAM database authentication policies), `kms_key_id`, `hosted_zone_id` and the rest of its attributes. The instances are in `rds_cluster_instance`, not in a `cluster_members` list.
- `rds_cluster_instance` - The instances, in order (`<name>-1` first), each with its `identifier`, `endpoint`, `availability_zone`, `writer` (whether it is the writer now), `instance_class`, `dbi_resource_id` and the rest of its attributes.
- `security_group` - The cluster's security group, with its `id`, `arn` and `name`. Use its `id` as a source in other groups' rules.
- `vpc_security_group_ingress_rule` - The ingress rules, keyed like `security_group_ingress`, or `null` when there are none.
- `vpc_security_group_egress_rule` - The egress rules, keyed like `security_group_egress`, or `null` when there are none.
- `cloudwatch_log_group` - The log groups, keyed by log type, each with its `name` and `arn`, or `null` when no logs are exported.
- `iam_role` - The Enhanced Monitoring role, with its `name` and `arn`, or `null` when `instances.monitoring_interval` is `0`.
- `iam_role_policy_attachment` - The attachment of `AmazonRDSEnhancedMonitoringRole` to that role, or `null`.
- `appautoscaling_target` - The Aurora Auto Scaling target, with its `min_capacity` and `max_capacity`, or `null` without `autoscaling`.
- `appautoscaling_policy` - The scaling policies, keyed `cpu` and `connections`, or `null` without `autoscaling`.
